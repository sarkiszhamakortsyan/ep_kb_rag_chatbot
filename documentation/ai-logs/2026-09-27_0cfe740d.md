A busy port no longer stops the chatbot from starting. Start it with `python3 scripts/start.py dev` or `python3 scripts/start.py docker`. If a preferred port is in use, it moves to the next free one and prints the addresses in use (this is how Vite already handles its own port).

| Command | Preferred ports | Change them in `.env` with |
|---|---|---|
| `python3 scripts/start.py dev` (backend + frontend on your machine) | backend 8000, frontend 5173 | `BACKEND_PORT`, `FRONTEND_DEV_PORT` |
| `python3 scripts/start.py docker [--claude-only]` | web UI 8080, Ollama 11434 | `FRONTEND_PORT`, `OLLAMA_PORT` |

What you see when ports are taken:

```

**How it behaves:**
- **Summary timing:** the addresses are printed only once the servers actually accept connections.
- **Frontend to backend:** the frontend's `/api` forwarding follows the backend to its new port.
- **Your own stack:** in Docker mode, a port already held by this project's running containers doesn't count as busy. Once 8080 is free again, the next start moves back to it.
- **Ollama port:** it can now be changed. `docker-compose.yml` reads `OLLAMA_PORT`, default 11434.
- **Stopping:** Ctrl+C stops both dev servers.
- **Plain `docker compose up`** doesn't check ports; it uses the values in `.env` as before.

**What I checked on the real setup:**
- **Dev mode:** with 8000 and 5173 taken, the servers came up on 8001 and 5174, and the chat page reached the backend. After stopping, no server process was left behind.
- **Docker mode, own containers:** with this project's containers already running, the stack stayed on 8080 and 11434.
- **Docker mode, 8080 taken:** with another program on 8080, the web UI moved to 8081 and printed that. When 8080 was free again, the next start moved it back.

Three problems came up in those runs and are fixed:
- The summary was printed before the backend could answer.
- A port was sometimes wrongly reported as busy just after an earlier connection to it had closed.
- Stopping left the Vite dev server running.
